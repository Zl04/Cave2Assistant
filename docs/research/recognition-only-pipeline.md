# 只识别文字的轻量流程

2026-10-14。当前正式入口仍为 PaddleOCRSDK 4.5.3，v5 mobile 检测 + v4 mobile 识别，CPU，方向分类已关闭；没有版面分析、表格分析或文档矫正。此前 tiny + DirectML 的约 68 ms 结果是独立实验，尚未接入正式程序。

## 本次验证

用原生 SDK 对同一实际截图做 `det=true` 与 `det=false` 对照。脚本 `outputs/adb_map_controller/tools/benchmark_recognition_only.py`，无需应用构建。包含 SDK PNG 解码、推理、JSON 解析；不含截图、裁剪编码、初始化，预热两次，无结果缓存。

现有标题区域为画面的 x=.35–.65、y=.03–.18，在两张样本上为 301×85，包含空白和其他画面元素，不能等同于文字行。

顺序运行、各 5 次的结果：

| 输入 | 检测+识别，中位数 | 只识别，中位数 | 只识别原文 |
|---|---:|---:|---|
| 贪婪混合弹窗标题区域 | 780 ms | 1191 ms | 贪基快择 |
| 下一层警告截图相同区域 | 132 ms | 532 ms | SeUSY |

第一张完整流程返回标题“贪婪块择”及若干低置信度装饰；第二张完整流程返回局部文字“亲爱的冒险”。第二张区域本来就不覆盖完整正文，不用于评估正文准确率。关闭检测输出不含坐标。

使用第一张检测框手工确定的 103×30 紧文字行，仅用于实验、不代表生产布局规则：

| 只识别线程数 | 样本数 | 中位数 | 原文 |
|---|---:|---:|---|
| 8 | 10 | 965 ms | 贪婪执择 |
| 1 | 10 | 244 ms | 贪婪执择 |

两轮时间窗口不同，机器存在 Unity 等后台程序，未隔离负载；样本较少，不能据此声称线程数是唯一原因或预计生产稳定耗时。较早并发对照也运行过，因相互竞争不用于性能结论。确定的正确性发现是：宽区域直接进入单行识别会产生错误文字，不能全局关闭检测。

复现：`python outputs/adb_map_controller/tools/benchmark_recognition_only.py --mode rec --tight --threads 1 --samples 10`。Pillow 用于内存裁剪，不产生临时截图。设置 `PYTHONDONTWRITEBYTECODE=1` 避免缓存。

## 推荐的范围

1. 单行文字：明确的文字行裁剪 → PP-OCRv6_tiny_rec → CTC 解码 → 字符串。不执行检测、方向分类、版面分析。普通文字也保留原文，不用关键词替代 OCR。
2. 整屏或多行文字：tiny 检测定位并切分行 → 批量 tiny 识别 → 按阅读顺序拼接字符串。只输出字符串不意味着识别模型能直接读取整张多行画面；检测坐标可仅在内部使用。
3. 输入高度与模型一致，宽度随文字长度，减少短行补到 320 的计算；会话复用、预热，优先复用此前验证过的 DirectML 紧凑输出路径。CPU 线程另做隔离负载下的对照，不直接全局改为 1。

官方 TextRecognition 模块可以独立调用，PP-OCRv6_tiny_rec 模型存储约 4.4 MB，现用 v4 mobile 为 10.5 MB；文件尺寸不能直接换算延迟。v6 与旧版准确率表采用不同评估集，不能直接比较准确率百分比。

来源：[Paddle 官方文字识别模块](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/module_usage/text_recognition.en.md)，[当前原生 SDK](https://github.com/PaddleOCRCore/PaddleOCRApi)。

本次未替换正式模型、未发布，也未新增自动点击行为。下一步应分别验收纯文字行入口与整屏字符串入口，再集成实际 C# 图像通路并复测；当前没有新的生产低于 100 ms 证据。
