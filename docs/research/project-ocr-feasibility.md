# 全项目文字识别轻量化可行性

2026-10-14，按当前工作区源码、实际调用与资源配置核对。结论：**分场景使用纯识别可行；全项目统一关闭检测不可行。tiny 识别 + 必要时 tiny 检测可覆盖当前需求，但仍需真实截图准确率验收。** 本文是静态调用审查，未改正式引擎，未新增性能承诺。

## 当前入口的关键约束

所有 OCR 最终进入 `PaddleOcrEngine.RecognizeAsync`，当前 v5 检测 + v4 识别、方向分类关闭。不存在文档版面分析、表格识别等可直接移除的重流程。

`AdbScreenAnalyzer.ReadTextAsync` 消费字符串；`ReadOcrWordsAsync` 消费带坐标的词。两者目前共享同一检测识别流程。后者过滤宽高为零的结果；引擎 `ToWord` 也依赖检测位置。因此仅把 `det` 改为 false，原生 SDK 返回空 Location 后，不仅点击定位失效，连只拼接词文本的调用也可能得到空集合。纯识别必须新增字符串入口，不能伪装成现有坐标接口。

## 需求逐项核对

“可改纯识别”表示业务无需文字坐标，不表示现有宽 ROI 能原样作为单行输入。须确定真实文字行、裁剪并验收。

## 推荐实现边界

保留两种明确语义：

- `ReadLineTextAsync`：输入已裁剪的单行图像，tiny_rec 输出字符串及置信度，不生成假文字框。
- `ReadOcrWordsAsync`：输入任意ROI/整屏图像，tiny_det + 批量 tiny_rec，返回与现有一致的原图坐标、文字和置信度。

多行但只消费文本的调用由后者的结果按行拼接即可，内部仍可使用检测框。固定多行也可以按已验证布局直接切分，但目前不同弹窗和分辨率未建立统一行布局规则，不能全局承诺免检测。

两种路径复用识别会话，常用规格预热；按文字长度选择输入宽度、批量处理，避免短行统一补宽。缓存必须区分模型、流程和输入规格，且点击前的新帧确认不能取消。tiny 采用此前验证的 DirectML 路线更有性能依据；现SDK的 `det=false` CPU实验并未稳定达到100ms。

先迁移数字/标题等不消费坐标的高频调用，再处理多行弹窗，最后迁移文字定位点击。所有改动必须满足：不同分辨率裁剪、阴性游戏画面不误报、文字及置信度正确、坐标偏移一致、难度与次数配对正确、出售/进图/点击前验证保留。

## 可行性结论的范围

流程层面可行，且多数当前整帧OCR是可以收紧区域的消息确认。纯识别不能覆盖全部功能；最合适的是轻量识别为核心、按需轻量检测的双入口。模型在全部中文标题、小数字、暗背景和弹窗上的准确率仍未验证完，本次不宣称全项目已达到100ms或可立即无条件替换。一次业务操作可能串行执行多轮OCR，单次引擎低于100ms也不等于整次预检低于100ms，应分别测单次、整个弹窗判断与启动预检。
